Decode a JWT locally without uploading the token

A compact signed JSON Web Token normally contains three dot-separated Base64URL sections: header, payload and signature. This decoder removes an optional Bearer prefix, decodes the first two sections as UTF-8 JSON and displays the third section exactly as it appears. Smart Web Utility does not send the token to a decoding API.

Header

Inspect fields such as alg, typ and kid. These values describe what the token claims about its signing metadata; they do not prove authenticity.

Payload

Read registered and application-specific claims carried by the token. A normal signed JWT payload is encoded, not encrypted.

Registered claims

The tool highlights iss, sub, aud, exp, nbf, iat and jti when present.

Signature segment

The raw third segment is visible for debugging and copying. This page does not verify it with a secret, public key or JWKS endpoint.

Check exp and nbf without confusing time checks with trust

JWT exp and nbf use the NumericDate convention defined by RFC 7519: seconds since the Unix epoch. The page converts numeric values to ISO dates and compares them with the current browser clock. It can show that a token is expired by exp or not active yet by nbf, but that result is not a validity verdict because the signature, issuer, audience and application policy remain unverified.

Decoding is not signature verification

Anyone can construct JWT-shaped text. A production application must verify the signature with the expected algorithm and trusted key, then validate the claims required by that application. RFC 8725 also warns implementations not to trust an attacker-controlled algorithm choice without an explicit verification policy. This decoder intentionally does not collect HMAC secrets, private keys or public keys.

Why Bearer tokens should still be treated as credentials

A bearer access token can grant API access while it remains valid. Local processing reduces one exposure path, but it does not make a live credential harmless. Prefer test or redacted tokens when possible, and avoid putting production tokens into tickets, screenshots, chats or shared notes.

Common JWT debugging scenarios

Expired access token

Inspect exp and compare the decoded timestamp with the application's clock, expected token lifetime and renewal flow.

Token not active yet

Review nbf when clock skew or an issuance delay could explain why an otherwise readable token is rejected.

Audience or issuer mismatch

Inspect aud and iss when an API expects a token from a different client, tenant, identity provider or environment.

Key selection

Check header values such as kid when a verifier selects among several trusted public keys. A displayed kid is metadata, not proof.

Scope and format limits

This page targets the common three-part compact signed-JWT shape. It does not decrypt JWE tokens, validate detached payloads, verify JSON serializations, call issuer metadata endpoints or fetch JWKS keys. It also warns when the header declares alg: none, but the warning is not a substitute for a verifier that rejects algorithms outside an explicit allowlist.

Frequently asked JWT questions

Can I paste an Authorization header value?

Yes. A leading Bearer prefix is removed before the JWT is split and decoded.

Can I trust a JWT because the page says it is not expired?

No. The time check only compares numeric exp/nbf claims with the browser clock. It does not verify the signature, issuer, audience or authorization policy.

Does this JWT decoder verify signatures?

No. It displays the signature segment but intentionally does not ask for secrets or keys and does not verify authenticity.

Is a JWT encrypted?

A typical signed JWT is not encrypted, so its header and payload can be decoded by anyone who has the token. JWE encryption is a separate JOSE mechanism.

Does this page store the token?

The decoding logic runs locally in browser JavaScript and does not submit the JWT to a Smart Web Utility API.
