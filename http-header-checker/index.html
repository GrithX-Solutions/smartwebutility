HTTP Header Checker

Inspect the HTTP response headers a public URL returns after safe redirects. Choose Auto, HEAD or GET and see the final URL, method used, status, timing, IP and repeated header values.

Result

Inspect the final HTTP response-header map

The checker makes a server-side request, follows at most three public redirects with every destination revalidated, and shows the raw headers from the final response. It also reports the requested and final URL, method used, response status, public IP, timing, header counts and any repeated header names.

Choose how the diagnostic requests the URL

Auto starts with HEAD because headers are the goal. If the server explicitly reports that HEAD is unsupported with HTTP 405 or 501, the checker retries that hop with GET and discards the response body as it arrives. You can also force HEAD or GET when comparing method-specific server behavior.

Cache behavior

Review headers such as cache-control, expires, age, etag and CDN-specific fields to understand how a response may be cached.

Redirect and final response

The report keeps the requested URL, final URL and a bounded status/location path visible while the raw table focuses on the final response. Use the Redirect Checker when you need deeper hop-by-hop redirect diagnosis.

Content metadata

content-type, content-length, compression and language-related headers describe the returned representation and can expose incorrect server configuration.

Repeated header values

Some response headers can appear more than once. The report preserves repeated values instead of silently replacing earlier fields, which matters for headers such as Set-Cookie and Link.

Headers worth checking

Content-Type identifies the representation. Content-Encoding can show compression. Cache-Control, ETag, Last-Modified and Vary provide caching evidence. Location appears on many redirect responses. Access-Control-* fields describe CORS behavior, while browser security policies include HSTS and Content-Security-Policy.

The report keeps these as raw evidence because the correct meaning depends on the application and response. Use the dedicated Security Headers Checker or Cache-Control Checker when you need policy-specific interpretation rather than a general header dump.

Common HTTP header troubleshooting scenarios

Changes are not appearing

Inspect cache-related headers and CDN fields. A stale response may be held by a browser, reverse proxy or edge cache even after the origin has changed.

Unexpected redirect

Check the HTTP status and location header, then use the Redirect Checker when you need to see every hop in a redirect chain.

Wrong file or MIME type

Check content-type. Incorrect MIME types can affect downloads, API clients, scripts, stylesheets and browser security behavior.

Security header review

Confirm that expected browser policies are actually present on the production response. The correct policy values depend on the application and should not be copied blindly.

Why your browser may show different headers

Responses can vary by cookies, authentication, user agent, geography, method, request headers, bot protection, CDN routing and experiments. This checker sends a server-side diagnostic request without your browser session, so use browser developer tools when you specifically need the headers returned to your own authenticated or personalized request.

What this checker does not prove

A header being present does not automatically make a site secure, fast or correctly cached. Likewise, a missing header is not always a vulnerability. Security and caching decisions depend on the application, resource type and intended behavior. This tool reports the response so you can diagnose it; it does not assign a security grade.

Frequently asked HTTP header questions

What is an HTTP response header?

It is metadata sent with an HTTP response before the response body. Headers can describe caching, media type, redirects, cookies, security policies, server behavior and other properties of the response.

Why is the Server header missing?

Many sites intentionally omit or minimize server-identification headers. A CDN or reverse proxy can also hide or replace the header sent by the origin server.

Why can HEAD and GET return different results?

Servers, applications, CDNs and security layers can handle HEAD differently from GET. Auto mode starts with HEAD and uses GET only when the server explicitly says HEAD is unsupported. Force a method when you need to compare behavior.

Can I use headers to check whether a page is cached?

Headers can provide strong clues, especially Cache-Control, Age, ETag and CDN-specific cache-status fields. Use the Cache-Control Checker when you need browser/shared-cache TTL interpretation and repeated-request evidence.

Does a 200 status mean the page is correct?

No. HTTP 200 only means the server returned a successful response at the protocol level. The body can still contain an application error, unexpected content or stale data.
