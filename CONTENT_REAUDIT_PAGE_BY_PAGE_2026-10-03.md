### Confirmed gap

RFC 9562 explicitly discusses monotonicity for UUID v7 generation and says implementations concerned with batches/high-frequency generation should add monotonic handling. The previous Smart Web Utility implementation generated a new unrelated random suffix for every v7 value.

That meant:
- UUID v7 values were time-ordered across different millisecond timestamps;
- values generated inside the same millisecond were not guaranteed to sort in generation order.

This was a real product gap because the page supports batches up to 1,000 and already positions v7 for time-ordered workflows.

### Implementation

`assets/uuid.js` now:
- keeps the last UUID v7 timestamp and 74-bit random payload in page-session memory;
- generates the 74-bit payload with Web Crypto;
- when the timestamp advances, seeds a fresh random payload;
- when another UUID is generated in the same millisecond, advances the previous payload by a cryptographically random positive increment;
- if the local clock moves backward, retains the previous logical timestamp and advances the payload;
- preserves RFC version and variant bits;
- handles the extremely unlikely 74-bit payload overflow by advancing the logical timestamp and reseeding.

Result:
- UUID v7 values generated by the current page session are lexicographically monotonic in generation order;
- separate tabs, browsers, devices and application processes remain independent and are not claimed to be globally monotonic.

### Content / semantic update

Updated visible copy to explain:
- what the same-session monotonic behavior means;
- why same-millisecond batches matter;
- that UUID v7 exposes creation time;
- that the guarantee does not coordinate independent generators;
- that distributed systems should enforce their own ordering requirements.

Updated WebApplication feature metadata and FAQ content to match the actual functionality.

Updated internal tool-search aliases with:

- `v4 uuid generator`
- `random uuid generator`

No new public URL was created.

### Test added

- verifies all 100 match UUID v7 + RFC variant syntax;
- verifies all 100 are unique;

This directly tests the gap rather than relying on ordinary real-time generation where timestamps could advance naturally.

### Confirmed gap

Modern installed web apps can apply OS-specific masks to app icons. MDN's current PWA guidance says:
- a web-app manifest can mark an icon with `purpose: "maskable"`;
- important artwork should stay inside the maskable safe zone;
- the guaranteed safe zone is a centered circle whose diameter is 80% of the icon's minimum dimension;
- maskable artwork should use an opaque background filling the icon area.

Before this page update, Smart Web Utility generated only ordinary 192×192 and 512×512 web-app icons. It did not produce dedicated maskable files and did not add `purpose: "maskable"` entries to the manifest.

Simply marking the ordinary icon as maskable would be incorrect when the user selects transparent output or puts artwork close to the edge.

### Implementation

`assets/favicon-generator.js` now:
- creates dedicated `android-chrome-192x192-maskable.png`;
- creates dedicated `android-chrome-512x512-maskable.png`;
- fills the full maskable canvas with the selected background color even when ordinary favicon transparency is enabled;
- keeps important source artwork inside a conservative square fully contained by the 80%-diameter safe-zone circle;
- adds explicit `purpose: "any"` to ordinary 192/512 manifest icons;
- adds dedicated `purpose: "maskable"` manifest entries for the new maskable files;
- includes both maskable PNGs in the ZIP.

The ordinary favicon/PWA icons remain separate so transparent and non-maskable use cases do not get silently changed.

### UX/content update

The page now:
- identifies maskable PWA icons in the hero/trust bar/package list;
- shows a dedicated 192×192 maskable preview;
- overlays the 80% safe-zone circle on that preview;
- explains why ordinary and maskable files are separate;
- explains the opaque-background requirement;
- documents the generated maskable filenames and manifest entries;
- links to current MDN PWA icon guidance.

The existing Google Search favicon guidance remains separate from PWA maskable-icon guidance. Google Search currently requires a square favicon of at least 8×8 px and recommends a favicon larger than 48×48 px; the page already documents that distinction.

### Security decision

The generator accepts SVG as source artwork but does not place the original uploaded SVG markup into the downloaded ZIP.

Reason:
- the browser renders the SVG source locally to safe raster PNG/ICO outputs;
- redistributing arbitrary uploaded SVG markup would preserve potentially active SVG content and would require a separate sanitization/security design;
- maskable support therefore uses generated PNG files rather than copying raw SVG source.

### Confirmed gap

The parser accepted a normalized nine-character permission value such as:
- `rwxr-xr-x`
- `rwsr-xr-x`
- `rwxrwxrwt`

But users commonly copy the permission field directly from `ls -l`, which includes a leading file-type character:
- `-rwsr-xr-x`
- `drwxrwxrwt`

The previous input had `maxlength=9` and rejected those normal 10-character strings.

### Technical reference

GNU Coreutils documents file permissions as permission mode bits plus special mode bits and explains the different semantics of read/write/execute for files versus directories. Current SERP tools also expose `ls -l`-style input because the leading character represents file type rather than a chmod permission bit.

### Implementation

`assets/chmod-calculator.js` now:
- accepts either 9 permission characters or a 10-character `ls -l` permission field;
- recognizes standard leading type characters used for regular files, directories, symlinks, block/character devices, pipes and sockets;
- ignores only that leading type character for chmod calculation;
- continues to parse `s/S/t/T` special-bit notation;
- normalizes the displayed symbolic result back to the nine chmod permission characters.

`chmod-calculator/index.html` now:
- allows 10 characters in the symbolic input;
- states that `ls -l` values can be pasted directly;
- explains that the leading file-type character does not change chmod permission bits;
- gives examples for setuid and sticky-directory modes;
- keeps the existing canonical intent rather than creating a separate “ls permissions calculator” page.

Search aliases now include:
- `linux chmod calculator`
- `chmod calculator online`
- `unix chmod calculator`
- `ls -l permissions`
- `octal permissions calculator`

### Regression tests

Chromium test now verifies:
- `-rwsr-xr-x` -> `4755`, normalized `rwsr-xr-x`, setuid detected;
- `drwxrwxrwt` -> `1777`, normalized `rwxrwxrwt`, sticky detected;
- existing octal, recursive command and umask behavior remains intact.

### Confirmed gap

A strong current competitor exposes both an octal chmod command and a symbolic chmod command. Smart Web Utility calculated symbolic display permissions but only generated the numeric terminal command.

GNU and BSD chmod support symbolic mode clauses using:
- classes `u`, `g`, `o`, `a`;
- assignment/add/remove operators;
- permissions including `r`, `w`, `x`, `s`, and `t`.

That makes an exact symbolic assignment a real task-completion feature, not keyword padding.

### Implementation

The result panel now generates two commands:

Octal:
- `chmod 755 file`
- `chmod 4755 file`
- recursive form when selected.

Symbolic assignment:
- `chmod u=rwx,g=rx,o=rx file`
- `chmod u=rwxs,g=rx,o=rx file` for setuid + execute;
- `chmod u=rws,g=rx,o=rx file` for setuid without owner execute;
- sticky/setgid bits are emitted in the appropriate class clause.

The assignment is generated directly from the same checkbox state as the numeric mode, so the two outputs describe the same final permission bits.

The UI now has separate Copy Octal and Copy Symbolic controls.

### Content / semantic update

Visible copy now distinguishes:
- an `ls -l` display string such as `rwsr-xr-x`;
- chmod symbolic assignment syntax such as `u=rwxs,g=rx,o=rx`;
- octal command syntax.

The recursive warning was also sharpened: applying one mode recursively can unintentionally make regular files executable when the operator only intended directory search permission.

Tool-search metadata now includes the exact `linux permissions calculator` variant.

The sitemap already carried a 2026-10-03 lastmod for this page, so no artificial freshness change was made.

### Test added
