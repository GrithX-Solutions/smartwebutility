Generate SHA digests locally in your browser

The Hash Generator uses the browser Web Crypto API to calculate SHA-1, SHA-256, SHA-384 or SHA-512. It encodes text as UTF-8 before hashing, reads selected files locally and passes their bytes directly to the browser's digest function. Smart Web Utility does not upload the file contents.

SHA-256

A widely used SHA-2 digest for checksums, integrity verification, content identifiers and many modern application workflows.

SHA-384 and SHA-512

Use these longer SHA-2 outputs when a protocol, policy or interoperability workflow requires them.

SHA-1

Use SHA-1 only for legacy compatibility and old checksum systems. Choose a stronger modern algorithm when collision resistance matters.

Hex output

Copy the digest as lowercase hexadecimal or toggle uppercase when matching a tool or checksum format that expects capital letters.

Verify a file checksum against the expected hash

Select the algorithm used by the checksum source, choose the local file and paste the expected digest. The verifier compares hexadecimal values without case sensitivity and can extract the digest from common checksum lines that also include a filename. A match means the bytes you hashed produced the same digest as the reference value.

A checksum match does not prove that a download is safe or that the publisher itself is trustworthy. Obtain the expected checksum from an authenticated source you trust; otherwise an attacker who replaces a file could also replace the checksum shown beside it.

Hashes are not encryption or password storage

A cryptographic hash is a one-way digest and does not make sensitive content confidential. Plain SHA algorithms are also not suitable password-storage schemes by themselves. Password systems should use a dedicated password-hashing or key-derivation design with salts and an appropriate work factor rather than storing a simple SHA digest of the password.

Text hashing details

The tool converts the text field to UTF-8 bytes before hashing. Small differences—including capitalization, spaces, line endings or invisible characters—change the input bytes and therefore change the digest. If two systems produce different hashes for “the same text,” compare their exact encoding and line-ending behavior.

Large-file considerations

The current browser implementation reads the selected file into memory before calculating the digest. That is convenient for normal files, but very large files can consume significant browser memory. Streaming command-line tools are better suited to unusually large disk images, backups or archives.

SHA algorithm scope

The browser Web Crypto digest() API supports SHA-1, SHA-256, SHA-384 and SHA-512, which is why this page focuses on those algorithms rather than adding unrelated password-hash formats. MDN documents the supported digest algorithms, and NIST FIPS 180-4 defines the Secure Hash Standard. SHA-1 remains available for legacy interoperability, but do not choose it for new cryptographic security designs.

Frequently asked hash questions

Will the same file always have the same SHA-256?

Yes, when both systems hash identical file bytes with the same algorithm. Even a one-byte change will normally produce a very different digest.

Can I reverse a SHA-256 hash to get the original file?

No practical inverse operation recovers the original value from a cryptographic hash. Hash functions work as one-way transformations, although an attacker can sometimes discover weak or guessable inputs by trying candidate values.

Why should I avoid SHA-1 for security-sensitive integrity?

Researchers have demonstrated practical collision attacks against SHA-1, so modern security designs generally use stronger SHA-2 family algorithms or another currently appropriate primitive.

Does the file leave my browser?

No. The current implementation reads the selected file locally and computes the digest using Web Crypto in the browser.

Can I paste a full checksum line instead of only the digest?

Yes. For the selected algorithm, the verifier can extract one correctly sized hexadecimal digest from a common checksum line such as a digest followed by a filename. If the line does not contain exactly one usable digest, it asks for a valid checksum instead of guessing.

Does a matching checksum prove a file is safe?

No. It proves that the calculated digest matches the reference value. The reference itself must come from a trustworthy source, and a checksum does not detect whether the original publisher intentionally distributed malicious content.
